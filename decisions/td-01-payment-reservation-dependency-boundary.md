# TD-01 — 결제↔예약 도메인의 순환 의존을 어떻게 풀었나

> 원본 분류: 기술적 의사결정 · 작성자: 김현승

## 구현 맥락

예약 취소 후 참여자별 PortOne 환불이 완료되면 Refund·Payment뿐 아니라 Participant·Reservation 상태도 하나의 완료 흐름으로 반영해야 했다.

기존에는 예약→결제 방향의 환불 요청 의존이 Port/Adapter로 분리돼 있었지만, 환불 완료 후에는 반대 방향인 결제→예약 통지가 필요해졌다. 이를 기존 서비스에 직접 연결하자 **Spring Bean 생성자 의존 그래프가 순환**해 애플리케이션이 기동하지 못했다.

## 요구사항

- Refund·Payment·Participant·Reservation 상태를 정합성 있게 반영할 것
- 즉시 응답과 Webhook이 같은 완료 로직으로 수렴할 것
- 도메인 간 Bean 순환 의존을 만들지 않을 것

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 직접 참조 | 가장 단순 | 기존 경계와 불일치, 결합 증가 |
| Port·Adapter | 기존 확정 흐름과 동일한 패턴 | 계층이 하나 더 생김 |
| Spring Event | 결합도 낮음 | 트랜잭션 경계가 달라져 정합성 창과 복잡성 증가 |
| 새 Orchestrator | 두 도메인의 직접 인지 감소 | 프로젝트에 없던 새 구조·책임 추가 |

## 결정

새 컴포넌트를 도입하기보다 **이미 프로젝트에서 문서화하고 검증한 Port·Adapter 패턴을 반대 방향 완료 통지에도 재사용**했다.

원인은 “결제와 예약이 서로를 안다”는 사실 자체가 아니라, **동일 Bean이 양방향 의존의 시작과 끝에 동시에 걸린 것**이었다. 완료 책임을 별도 클래스로 분리해 임시 우회였던 `ObjectProvider` 기반 순환 회피 구조를 제거할 수 있게 했다.

## 왜 Event로 바로 바꾸지 않았나

Spring Event는 결합도를 더 낮출 수 있지만 현재 완료 처리에서는 여러 상태를 한 트랜잭션에서 일관되게 반영하는 요구가 우선이었다. 새로운 비동기/트랜잭션 경계를 추가하기 전에 현재 동기 구조가 실제 병목인지 측정해야 한다고 판단했다.

향후 Webhook 동시 처리에서 락 대기·응답시간·처리량을 k6로 측정하고 실제 병목이 확인될 때 Event 기반 분리를 재검토한다.

## 배운 점

- 순환 의존은 도메인 관계보다 **Bean 책임과 의존 그래프**를 먼저 봐야 한다.
- 이론적으로 더 세련된 새 구조보다 **프로젝트에서 이미 합의·검증한 패턴과의 일관성**이 더 강한 판단 근거일 수 있다.
- 성능 문제는 구조를 복잡하게 만들기 전에 실측으로 확인한다.
